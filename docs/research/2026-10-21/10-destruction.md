# Real physics and destruction in Godot 4.x (Jolt, fracturing, voxel destruction, debris budgets, GDExtension)

Researched 2026-10-21. Repo check (read only): `project.godot` already sets `3d/physics_engine="Jolt Physics"`.

## Key findings

1. **Jolt is built into Godot and is the default for new projects since 4.6.** Godot 4.4 added Jolt as an experimental built-in engine module. Godot 4.6 (released 27 Jan 2026) made it the default for new projects only; existing projects keep their setting ([Godot 4.6 release page](https://godotengine.org/releases/4.6/); [Godot docs: Using Jolt Physics](https://docs.godotengine.org/en/latest/tutorials/physics/using_jolt_physics.html); [desdelinux summary](https://blog.desdelinux.net/en/Godot-4.6-release-Jolt-Physics-IK-modern-theme/)). The standalone godot-jolt GDExtension (MIT) is in maintenance mode, fixes only, and its README says the repo "will likely be archived" once the module reaches parity ([godot-jolt README](https://github.com/godot-jolt/godot-jolt)). The 4.7 notes found cover only Jolt soft-body changes (default mass 1 kg, stiffness retune) and Area3D/soft-body overlaps; nothing on rigid-body determinism ([Upgrading to 4.7](https://docs.godotengine.org/en/4.7/tutorials/migrating/upgrading_to_godot_4.7.html); [4.7 beta 1](https://godotengine.org/article/dev-snapshot-godot-4-7-beta-1/)). A proposal to make Jolt the default for existing projects in 4.7 and drop GodotPhysics3D in 4.8 is a proposal, not a confirmed plan ([godot-proposals #12289](https://github.com/godotengine/godot-proposals/issues/12289)).

2. **Jolt the library is deterministic under strict conditions, but Godot's integration does not promise it.** Jolt's docs say a simulation is deterministic only if (a) every API call that changes the simulation (add, remove or modify bodies and constraints) happens in exactly the same order, and (b) the same binary runs it. The `CROSS_PLATFORM_DETERMINISTIC` CMake option extends this across compilers, OSes and CPUs at about 8% speed cost. It also needs precise FP mode, no FP contraction, matching rounding/DAZ/FTZ, and Jolt's own trig, sort and hash. Broadphase query results, contact/activation listener callback order and `GetActiveBodies` order are non-deterministic across threads and must be sorted by the caller ([Jolt docs, Deterministic Simulation](https://jrouwe.github.io/JoltPhysics/index.html); [JoltPhysics README, MIT](https://github.com/jrouwe/JoltPhysics)). The godot-jolt maintainer is explicit: "While Jolt itself offers deterministic simulations, Godot Jolt is not able to make such guarantees" ([godot-jolt README](https://github.com/godot-jolt/godot-jolt)). Godot's own Jolt doc says nothing about determinism and calls "Run On Separate Thread" experimental ([Godot docs](https://docs.godotengine.org/en/latest/tutorials/physics/using_jolt_physics.html)). Inference: Godot's node/scene order, signal-driven body creation, the physics-interpolation path and the default compiler flags of official builds are all outside Jolt's guarantee. Honest answer: physics running through Godot's Jolt is not replayable, and it would not pass this repo's determinism rule.

3. **Rapier (godot-rapier-physics) is the only Godot physics add-on that claims cross-platform determinism, but its 3D side is incomplete.** Rapier (Rust, **Apache-2.0**, [dimforge/rapier](https://github.com/dimforge/rapier)) is locally deterministic by default. It becomes cross-platform deterministic with the `enhanced-determinism` feature on IEEE 754 targets, given the same construction and insertion order. That feature cannot be combined with `simd8`, while the `parallel` solver gives the same results as the sequential one ([Rapier determinism guide](https://rapier.rs/docs/user_guides/rust/determinism/)). The Godot add-on (**MIT**) targets Godot 4.4 to 4.7, ships with `enhanced-determinism` on, and claims cross-platform determinism. Its own README says "the 3D part is still missing some things", gives no benchmarks against Jolt, and discloses AI-assisted development ([godot-rapier-physics README](https://github.com/appsinacup/godot-rapier-physics)). A "Determinism Fix" for saved-state congruence landed only in v0.8.28 ([godot.rapier.rs v0.8.28](https://godot.rapier.rs/blog/v0-8-28)), which suggests replay determinism through Godot is recent and lightly proven.

4. **Rigid-body budgets: thousands at best, and every source is weak.** Rapier's vendor-run benchmark (Godot 4.3 beta, rendering off, count until fps < 30) gives about 1,500 boxes/spheres for GodotPhysics3D and about 5,000 for Jolt 0.13 ([godot.rapier.rs performance](https://godot.rapier.rs/docs/documentation/performance)). A forum user reported about 900-1,000 bodies with GodotPhysics versus about 3,100 with Jolt ([jMonkeyEngine forum](https://hub.jmonkeyengine.org/t/i-compared-jmonkeyengine-3-6-with-godot-4-2/47696)). An unverified blog table claims 1,000 boxes at 60 fps with Jolt in 4.6, and 10,000 at 19 fps ([StraySpark blog](https://www.strayspark.studio/blog/godot-46-jolt-physics-migration-guide)). Inference: with a sim, a 4K render, carving and AI sharing the frame, plan on a few hundred *awake* Jolt bodies with simple box colliders, not thousands. Measure it on this PC before committing.

5. **Physics-free debris scales by orders of magnitude more.** Godot describes MultiMesh as a single draw primitive that "can draw up to millions of objects in one go". Culling is all or nothing per MultiMesh, so split by area or building. The fast update path is to build the buffer in C++ (threads allowed) and push it with `RenderingServer.multimesh_set_buffer()`, or to animate per instance in the vertex shader via `INSTANCE_ID`/`INSTANCE_CUSTOM`. GDScript per-instance loops are fine only for a few thousand ([Godot docs: MultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)). GPUParticles3D cannot see the physics world. They collide only with dedicated colliders: box, sphere, a runtime heightfield (update "When Moved", or "Always" at a cost, with an optional follow-camera mode), and a baked static SDF that is **not supported in gl_compatibility** and cannot change at runtime ([Godot docs: particle collision](https://docs.godotengine.org/en/stable/tutorials/3d/particles/collision.html)). Inference: a heightfield collider that rebuilds as buildings fall is the only particle-collision option that works in both renderers and follows destruction.

6. **Shipped destruction games run custom solvers or pre-broken structures with stress rules, not off-the-shelf rigid-body worlds.** Red Faction: Guerrilla's Geo-Mod 2.0 used pre-broken meshes linked into a stress-based collapse model, replacing the earlier real-time CSG ([Red Faction wiki: Geo-Mod 2.0](https://www.redfactionwiki.com/wiki/GeoMod_2.0); [WhatCulture](https://whatculture.com/gaming/10-video-games-that-blew-your-mind-without-you-realising-2), a secondary source). No primary GDC talk was found. Teardown's author wrote a custom voxel physics engine: sub-stepping in place of solver iterations, plus a parallel solver for big piles, about 5 ms on a 32-thread i9 ([80.lv](https://80.lv/articles/see-what-s-new-in-teardown-creator-s-custom-voxel-physics-engine/)). Tuxedo Labs also prototyped a separate structural-integrity system ([80.lv demo](https://80.lv/articles/this-real-time-voxel-building-demolition-is-so-satisfying/)). Their own blog says syncing that physics over a network is "already known to be hard" ([blog.voxagon.se](https://blog.voxagon.se/)). Instruments of Destruction, led by an ex-RF:G designer, places joints selectively, not per voxel. That rests on a player forum post, so it is weak ([Steam discussion](https://steamcommunity.com/app/1167630/discussions/0/2918850377439305091); [Xbox Wire](https://news.xbox.com/en-us/2025/10/24/instruments-of-destruction-explodes-onto-xbox-series-xs-today/)).

7. **Disconnected-chunk detection is flood fill to ground anchors. Union-find cannot split.** The common game pattern is: after a removal, search for voxels that lost their path to an anchor, then detach them ([Roblox devforum voxel engine](https://devforum.roblox.com/t/my-non-destructive-voxel-destruction-engine/3980658); [ExtroForge tech demo](https://www.moddb.com/games/extroforge/news/extroforge-tech-demo-1-voxel-destruction)). Union-find (disjoint sets over adjacent pairs) labels components in one pass, but supports only merges, so after deletions it must be rebuilt or swapped for a bounded flood fill ([GameDev.net thread](https://gamedev.net/forums/topic/714520-determine-if-two-voxels-are-in-the-same-assembly)). Unsourced inference: the cheap incremental form runs a bounded BFS from each former neighbour of the removed voxels. A search stops early once it reaches an anchor or another search's visited set. Only the searches that exhaust without reaching an anchor yield a floating island. Cost scales with the island's size, not the building's. Running it on a coarse chunk/brick graph first (for example 4^3 bricks) cuts the work further.

8. **Merging voxels into boxes makes colliders viable.** Merging adjacent voxels into larger boxes (greedy merge) turns a wall of hundreds of voxel colliders into one or a few ([jMonkeyEngine forum](https://hub.jmonkeyengine.org/t/interesting-voxel-solution/42210)). Combined with finding 4, a falling chunk should get a handful of greedy-merged boxes (or one oriented box), never per-voxel shapes.

## For Kaiju Incremental

Ranked, simplest viable first. The rule throughout: **the sim decides what breaks, what detaches and where it lands. Physics engines only ever decorate.**

1. **Sim-driven, deterministic topple in the existing C++ carve library (keep, do not swap for Jolt).** When carving cuts a chunk off from ground anchors, the sim gives it a seeded, closed-form fall: a hinge pivot on the last support edge, angular acceleration from the chunk's mass and centre (integer or fixed-step maths), and a landing footprint that carves or damages what it hits. Presentation animates the chunk's mesh along that path from a sim event. *Cost:* moderate C++ inside a library that already exists. Fully headless-testable with pinned seeds, zero physics budget, replays bit-exact. This is what Red Faction: Guerrilla (stress model) and Teardown (custom solver) did in spirit: owned destruction rules, not a stock rigid-body world.
2. **Island detection: bounded flood fill on a brick graph, run after each carve batch.** Keep a coarse brick graph (for example 4x4x4 voxel bricks) per building. After a carve, run BFS from the touched bricks' neighbours to anchors, with early exit, and refine to voxels only inside the island's boundary bricks. Rebuild the union-find labels lazily when a building is idle. *Cost:* small to moderate C++. Deterministic if neighbour order is fixed. Cost scales with the island, not the city.
3. **Debris as presentation-only MultiMesh with shader ballistics, seeded from the sim event.** Each break event carries a seed and an impulse; the vertex shader integrates `p = p0 + v*t + g*t^2/2` with a ground clamp, then a "settle" state. After N seconds the pieces fold into a static rubble mesh or decal, which the sim can also record as rubble cells. One MultiMesh per building or area, with a fixed pool and `visible_instance_count`. *Cost:* one shader plus one pool class. Works in Forward+ and gl_compatibility. Budget in the tens of thousands of instances. No CPU physics.
4. **GPU particles for dust and small chips only, with one camera-following heightfield collider.** Use `GPUParticlesCollisionHeightField3D` (follow camera, update "When Moved" or a throttled refresh). Do not use SDF colliders: they are static and Forward+-only. *Cost:* low; resolution and update mode are the only knobs.
5. **Optional eye candy: a capped Jolt pool for big chunks the player watches up close.** Use the already-selected built-in Jolt with greedy-merged box colliders (one to a few per chunk). Hard cap a few hundred awake bodies, short lifetimes, sleep, then freeze to static, then despawn into rubble. Never read their positions back into the sim, never use them for hits on tanks or helicopters, and accept that replays will differ visually here. *Cost:* CPU frame time, which must be measured on this PC. It adds a non-deterministic visual layer, so it needs a clear "presentation only" boundary in code review.
6. **Tanks and helicopters: sim-kinematic, not RigidBody3D.** Move them by sim maths (steering, seeded AI) and render as nodes. Hits come from sim geometry queries against the voxel grid and chunk paths, not physics contacts. *Cost:* none beyond the current sim. It avoids Jolt's non-deterministic query and callback order.
7. **Last resort, only if gameplay-relevant rigid bodies become a must: own the solver.** Options: Jolt linked directly in the existing GDExtension, built with `CROSS_PLATFORM_DETERMINISTIC`, single-threaded or with sorted callbacks, and every add/remove in sim order (MIT, about 8% slower). Or Rapier via its own crate with `enhanced-determinism` (Apache-2.0). Or a tiny custom brick-body integrator. *Cost:* high, weeks of work plus a determinism test harness. godot-rapier's 3D side is incomplete and its determinism fix is recent, so do not adopt it for the sim.

## Evidence gaps
- No primary benchmark exists for Jolt body counts in Godot 4.6/4.7; the figures are vendor-run (Rapier), anecdotal or unverified, so measure on the director's PC.
- No primary RF:G GDC talk or Teardown write-up on island detection was retrieved.
- "CityV" could not be identified online (possibly only the reference video).
- Whether Godot 4.7 made Jolt the default for existing projects was not confirmed (moot here: the repo already uses Jolt).
- godot-jolt issue #301 (determinism) was not read.
- The incremental flood-fill design in finding 7 is my inference, not a cited source.
